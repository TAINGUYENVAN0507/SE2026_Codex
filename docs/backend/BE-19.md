# Hướng dẫn Khắc phục sự cố và Giám sát Hệ thống (BE-19)

Tài liệu này mô tả kiến trúc quan sát (observability), cấu trúc log JSON, endpoint Prometheus `/metrics`, và quy trình từng bước điều tra, khắc phục sự cố khi một tiến trình xử lý cuộc họp (`job_id`) gặp lỗi.

---

## 1. Tổng quan Kiến trúc Quan sát (BE-19)

Hệ thống cung cấp hai cơ chế giám sát vận hành chính:
1. **Structured JSON Logging**: Toàn bộ log của API và Worker được định dạng JSON chuẩn qua `JSONLogFormatter` (`app/core/logging.py`), tuân thủ chặt chẽ nguyên tắc bảo vệ quyền riêng tư (PRIV-10):
   - Tuyệt đối **không** ghi nội dung nhạy cảm: tiêu đề cuộc họp, transcript, audio path, token JWT hoặc thông tin cá nhân.
   - Giữ lại đầy đủ các trường kỹ thuật có cấu trúc theo chuẩn ROADMAP: `event`, `job_id`, `meeting_id`, `request_id`, `worker_id`, `stage`, `attempt`, `error_code`, `duration_sec`, `status`.
2. **Prometheus Metrics (`/metrics`)**:
   - Endpoint độc lập đặt tại `/metrics` (không thuộc `/api/v1` và `include_in_schema=False`).
   - Nhãn `route` luôn sử dụng template chuẩn (ví dụ: `/api/v1/meetings/{meeting_id}`), tuyệt đối không để lộ UUID trong labels.
   - Thống kê thời gian thực trạng thái hàng đợi và lỗi job trực tiếp từ cơ sở dữ liệu tại thời điểm scrape.

---

## 2. Các Số đo Prometheus Chính

| Metric | Loại | Nhãn (Labels) | Ý nghĩa |
|---|---|---|---|
| `http_requests_total` | Counter | `method`, `route`, `status` | Tổng số HTTP requests đã xử lý theo template route. |
| `http_request_duration_seconds` | Histogram | `route` | Phân phối thời gian xử lý HTTP request (giây). |
| `jobs_total` | Gauge | `status` | Số lượng background jobs theo trạng thái (`queued`, `running`, `retry_scheduled`, `succeeded`, `failed`, `cancelled`). |
| `job_oldest_queued_seconds` | Gauge | *(không có)* | Độ tuổi (giây) của job đang nằm trong hàng đợi lâu nhất. |
| `jobs_failed_total` | Gauge | `stage`, `error_code` | Số lượng job thất bại gom theo stage và mã lỗi kỹ thuật. |
| `pipeline_stage_duration_seconds` | Histogram | `stage` | Phân phối thời gian thực thi từng stage trong pipeline (giây). |

## 3. Quy trình Từng bước Điều tra Lỗi từ một `job_id`

Khi nhận được phản ánh sự cố hoặc cảnh báo từ người dùng kèm một `job_id`, thực hiện các bước sau để xác định nguyên nhân gốc rễ (Root Cause Analysis):

### Bước 1: Tra cứu Nhật ký JSON theo `job_id`

Sử dụng công cụ dòng lệnh (hoặc dashboard quản lý log như Grafana Loki, CloudWatch):

```bash
# Lọc toàn bộ sự kiện liên quan tới job_id
grep '"job_id": "9c288a72-d7c6-4b0e-b377-6c6bb1953551"' logs/app.log | jq .
```

### Bước 2: Đối chiếu Vòng đời Sự kiện (Event Lifecycle)

Một job thông thường sẽ trải qua chuỗi sự kiện có cấu trúc:
1. `job_created`: Sinh ra khi API tiếp nhận yêu cầu (`POST /api/v1/meetings` hoặc `POST /api/v1/meetings/{id}/jobs`):
   ```json
   {
     "timestamp": "2026-11-06T07:19:40.950175+00:00",
     "level": "INFO",
     "logger": "backend.api.meetings",
     "message": "Job 9c288a72-... đã được tạo cho cuộc họp a5b92e1e-...",
     "request_id": "3e60a69a-1541-4d16-a829-562208409f16",
     "event": "job_created",
     "job_id": "9c288a72-d7c6-4b0e-b377-6c6bb1953551",
     "meeting_id": "a5b92e1e-4848-4a16-92df-157006548ede",
     "stage": "preprocess",
     "attempt": 1,
     "status": "queued"
   }
   ```
2. `job_claimed`: Sinh ra khi Worker nhận quyền thực thi từ hàng đợi:
   ```json
   {
     "timestamp": "2026-11-06T07:19:40.955311+00:00",
     "level": "INFO",
     "logger": "backend.worker",
     "event": "job_claimed",
     "job_id": "9c288a72-d7c6-4b0e-b377-6c6bb1953551",
     "worker_id": "worker-prod-01",
     "stage": "preprocess",
     "attempt": 1,
     "status": "running"
   }
   ```
3. `job_failed` hoặc `job_retry_scheduled`: Sinh ra khi gặp lỗi trong pipeline:
   - Nếu là lỗi tạm thời (`TransientPipelineError`) và còn lượt thử (`attempt < max_attempts`):
     Ghi nhận event `job_retry_scheduled` kèm thời gian chờ theo thuật toán exponential backoff và jitter.
   - Nếu là lỗi vĩnh viễn (`PermanentPipelineError`) hoặc hết số lượt thử tối đa:
     Ghi nhận event `job_failed`:
     ```json
     {
       "timestamp": "2026-11-06T07:19:41.409796+00:00",
       "level": "ERROR",
       "logger": "backend.worker",
       "event": "job_failed",
       "job_id": "9c288a72-d7c6-4b0e-b377-6c6bb1953551",
       "worker_id": "worker-prod-01",
       "stage": "preprocess",
       "attempt": 1,
       "error_code": "AUDIO_INVALID",
       "status": "failed"
     }
     ```

### Bước 3: Xác định Stage và Mã lỗi

Từ log sự kiện `job_failed`:
- **Stage**: Xác định chính xác bước xử lý bị gãy (`preprocess`, `vad`, `asr`, `diarize`, `merge`, `summarize`).
- **Error Code**: Tra cứu danh mục mã lỗi chuẩn:
  - `AUDIO_INVALID`: Tệp âm thanh không đọc được hoặc cấu trúc header bị hỏng.
  - `NO_SPEECH_DETECTED`: VAD không tìm thấy giọng nói hợp lệ trong tệp.
  - `DIARIZATION_FAILED`: Lỗi phân đoạn hoặc nhận diện người nói.
  - `LLM_API_ERROR` / `SUMMARY_FAILED`: Lỗi kết nối dịch vụ tóm tắt.
  - `LEASE_TIMEOUT`: Worker bị mất khóa lease do quá hạn heartbeat.

### Bước 4: Kiểm tra Trạng thái trên API và Metrics

1. Truy vấn trạng thái job qua API backend:
   ```bash
   curl -H "Authorization: Bearer <TOKEN>" https://api.codex.local/api/v1/jobs/9c288a72-d7c6-4b0e-b377-6c6bb1953551
   ```
2. Kiểm tra chỉ số `/metrics` để xem xu hướng lỗi chung trên hệ thống:
   ```bash
   curl https://api.codex.local/metrics | grep jobs_failed_total
   ```
   Kết quả trả về:
   ```
   jobs_failed_total{error_code="AUDIO_INVALID",stage="preprocess"} 3.0
   jobs_failed_total{error_code="DIARIZATION_FAILED",stage="diarize"} 1.0
   ```

## 4. Số liệu Đo lường Thực tế (Measured Test Timings)

Dưới đây là các số đo thực tế ghi nhận trong quá trình thực hiện kiểm thử tự động tại môi trường phát triển (Python 3.12, Windows x64, SQLite in-memory / LocalStorage):

1. **Thời gian đáp ứng của Endpoint `/metrics`**:
   - Lần scrape đầu tiên (khởi tạo gauge DB query): **21.97 ms**
   - Các lần scrape định kỳ tiếp theo: **3.72 ms - 6.49 ms**
2. **Thời gian ghi nhận và chuyển trạng thái Job**:
   - `create_meeting` (bao gồm upload WAV 100 bytes, probe metadata và enqueue job): **32.38 ms**
   - Worker claim job từ hàng đợi: **4.13 ms**
   - Pipeline xử lý và phát hiện lỗi permanent ở stage `preprocess`: **454.48 ms**
   - Phản hồi endpoint chi tiết cuộc họp `GET /api/v1/meetings/{id}`: **23.31 ms - 24.19 ms**
3. **Phân phối Histogram Request Duration**:
   - Khoảng 95% request API hoàn thành trong nhóm bucket `le="0.05"` (dưới 50 ms).
   - Chỉ các request upload hoặc truy vấn dữ liệu nặng mới chạm bucket `le="0.25"`.

## 5. Chẩn đoán Stage Xử lý Chậm (Diagnosing Slow Stages)

Khi tổng thời gian xử lý một cuộc họp kéo dài hoặc vượt quá SLA (ví dụ p95 > 3.0 giây cho kiểm thử tải hoặc các phiên họp dài), kỹ sư vận hành sử dụng metric `pipeline_stage_duration_seconds` để xác định chính xác stage gây nghẽn (bottleneck).

### 5.1. Cơ chế Thu thập Metric

- Worker runner (`app/worker/runner.py`) nhận đối tượng `PipelineOutcome` từ pipeline sau khi hoàn tất các stage.
- Trường `outcome.timings` chứa từ điển thời gian thực thi (giây) của từng stage: `preprocess`, `vad`, `asr`, `diarize`, `merge`, `summarize`.
- Worker ghi nhận từng thời lượng vào Histogram `pipeline_stage_duration_seconds` với nhãn duy nhất `stage`.
- **Nguyên tắc bảo vệ dữ liệu (PRIV-10):** Nhãn metric tuyệt đối chỉ chứa tên stage kỹ thuật (`preprocess`, `vad`, `asr`, `diarize`, `merge`, `summarize`), không chứa `job_id`, `meeting_id`, `user_id` hay bất kỳ UUID nào.

### 5.2. Các Truy vấn PromQL Chẩn đoán Trọng yếu

1. **Thời gian thực thi trung bình của từng stage (5 phút gần nhất):**
   ```promql
   rate(pipeline_stage_duration_seconds_sum[5m]) / rate(pipeline_stage_duration_seconds_count[5m])
   ```
   Giúp xếp hạng các stage theo thời gian trung bình để tìm stage tiêu tốn nhiều thời gian nhất.

2. **Phân vị 95 (p95) thời gian thực thi theo từng stage:**
   ```promql
   histogram_quantile(0.95, sum(rate(pipeline_stage_duration_seconds_bucket[5m])) by (le, stage))
   ```
   Xác định stage có đuôi trễ (tail latency) cao, phát hiện hiện tượng bất thường khi tải tăng.

3. **Tổng thời gian pipeline tiêu thụ cho từng stage:**
   ```promql
   sum(rate(pipeline_stage_duration_seconds_sum[1h])) by (stage)
   ```

### 5.3. Quy trình Xử lý Sự cố theo Từng Stage Chậm

| Stage Bị Chậm | Nguyên nhân Thường gặp | Biện pháp Khắc phục Đề xuất |
|---|---|---|
| `preprocess` | Tệp âm thanh định dạng nén phức tạp hoặc đĩa I/O bị nghẽn | Tối ưu hóa ffmpeg subprocess, chuyển thư mục tạm sang NVMe SSD. |
| `vad` | Âm thanh có độ ồn nền lớn, thuật toán silero phân đoạn liên tục | Tinh chỉnh ngưỡng năng lượng hoặc lọc ồn trước khi phân đoạn. |
| `asr` | Mô hình Whisper kích thước lớn chạy trên CPU; audio dài | Bật GPU inference (CUDA) hoặc dùng model nhỏ hơn (`base` / `small`) cho phiên họp thông thường. |
| `diarize` | Nhiều người nói xen kẽ hoặc mô hình clustering tốn RAM | Giới hạn số lượng embedding clusters hoặc chạy chế độ fallback 1-speaker nếu không bắt buộc. |
| `summarize` | LLM API phản hồi chậm, rate limit hoặc prompt quá dài | Giảm bớt ngữ cảnh trích dẫn, áp dụng LLM streaming hoặc cấu hình timeout hợp lý. |
